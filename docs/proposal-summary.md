> 공식 예시 매핑: **청년 창업 매칭 및 시드 금융 연결 AI**
> 작성 2026-09-18 · 저장소 `github.com/localhostdaegu/cloud.localhostdaegu`

## 한 줄 요약

**대구에서 점포 계약을 검토 중인 예비창업자가, 자기 조건으로 창업자금을 계산하고 조건을 바꿔 비교한 뒤, 은행에 무엇을 물어볼지 정리된 상담 준비자료를 들고 iM뱅크 창구로 가게 하는 서비스.**

---

## 1. 우리가 본 문제

창업 계산기는 이미 많다. 그런데 **희망대출 2,500만 원**을 입력하면 대부분 이렇게 답한다.

> 부족액 0원 — 자기자본으로 충분합니다

**그 2,500만 원은 아직 빌리지 않은 돈이다.** 예비창업자는 "충분하다"는 화면을 보고 은행에 갈 이유를 잃는다. 실제로는 2,260만 원을 어디서 조달할지 상담해야 하는 상황인데도.

상권분석 서비스는 "이 자리는 위험합니다"에서 끝나고, 계산기는 숫자 하나를 던지고 끝난다. **둘 다 "그래서 은행에 가서 뭘 물어야 하는가"에 답하지 않는다.**

## 2. 해결 — 하나의 흐름

```
지도에서 자리 선택
   ↓
창업 단계 입력 (사업자등록 여부·개업 예정일·자금 필요일)
   ↓
비용·자금·매출 가정 입력  →  계산  →  최초안 고정
   ↓
조건 수정 (예: 월세 250만 → 100만)  →  재계산  →  현재안
   ↓
[최초안] vs [현재안] 비교  →  상담할 안 선택  +  변경 이유 작성
   ↓
상담 준비자료 (계획·비교·계산·자금 후보·확인할 질문)
   ↓
Markdown 저장 / 인쇄  →  iM뱅크 공식 상담 경로
```

## 3. 핵심 차별점 셋

### ① 자금 숫자를 네 갈래로 분리한다

```
운영준비금        = 월 고정비 × 6개월
총 준비자금       = 초기 투자비 + 운영준비금
자기자본 외 조달 필요 = 총 준비자금 − 자기자본          ← 상담해야 할 금액
희망대출 반영 후 부족액 = 총 준비자금 − 자기자본 − 희망대출  ← 기존 계산기가 보여주던 값
```

앞의 사례(자기자본 4,000만·희망대출 2,500만·월세 100만)를 실제 엔진에 넣으면:

| 값 | 금액 |
|---|---:|
| 총 준비자금 | 62,600,000원 |
| 자기자본 외 **조달 필요** | **22,600,000원** |
| 희망대출 반영 후 부족액 | 0원 |

부족액이 0원이어도 **2,260만 원이 상담 주제로 남는다.** 화면에서 "자기자본으로 충분해요" 문구를 제거했고, 미확보 희망대출을 별도로 표시한다.

### ② 계산은 코드가, 설명만 AI가

비교표·계산표는 **LLM을 거치지 않는 결정론 코드**가 만든다. AI는 이미 계산된 값을 읽고 변경 이유를 설명하고 상담 질문을 쓴다. 숫자 환각이 구조적으로 불가능하다. LLM 생성이 실패해도 계산표와 확인 목록은 남는다.

클라이언트가 보낸 계산 결과도 리포트의 기준으로 쓰지 않는다. 서버가 입력 13필드로 다시 계산한다.

### ③ 근거를 확인한 상품만 은행 후보로

운영 상품 12건의 **공식 원문을 전부 대조**했다(`docs/research/finance-products/2026-09-18-consultation-sources.md`).

| 등급 | 건수 | 판정 근거 |
|---|---:|---|
| `direct` | 2 | iM뱅크 자사 상품 페이지에 게시 |
| `linked` | 3 | 지자체·재단 공고나 보도가 iM뱅크를 취급처로 명시 |
| `unverified` | 7 | 취급 은행이 "시중은행" 등으로만 표기 |

**iM뱅크 취급이 확인된 상품만 "iM뱅크에서 상담할 상품"으로 보여주고, 나머지는 "차선 후보 — iM뱅크 취급 미확인"으로 분리한다.** 준비서류를 확인하지 못했으면 "공식 안내에서 확인 필요"라고 적지, 그럴듯한 목록을 지어내지 않는다.

조사 과정에서 대구신용보증재단 사이트가 **중간 인증서를 보내지 않는 TLS 설정 오류**로 접근되지 않았는데, 검증을 끄지 않고 발급자 정보로 체인을 복원해 원문을 확인했다.

## 4. 왜 은행이 붙일 수 있는가

- **상담 전 단계에서 고객이 정리된다.** 자금 수요·계산 근거·변경 이유·미확인 항목이 한 문서로 온다.
- **상품 안내가 은행 기준으로 정렬된다.** iM뱅크 자사 취급 → 연계 → 미확인 순이며, 이 순위가 기존 보증·정책자금 정렬보다 우선한다.
- **과장하지 않는다.** 승인·한도·금리를 보장하지 않으며 그 사실을 문서에 박아 둔다. 은행이 그대로 붙여도 고객 민원이 생기지 않는 표현 수준을 목표로 했다.

**현재 제휴는 없다.** 공개된 공식 채널 안내만 구현했고, 사용자가 자료를 저장해 직접 지참한다. 상담 유입·전환은 검증하지 않은 사업 가설이다.

## 7. 구현하지 않은 것 (명시)

심사·시연에서 구현된 것처럼 설명하지 않기 위해 적는다.

- **은행 전송·상담 예약·대출 신청 연계 API** — 제휴·제공 여부 미확인. 사용자가 자료를 지참한다
- **신용조회·사전심사·승인 가능성 판정**
- **블록체인 앵커링** — 이번 범위에서 제외했다. 상담자료 무결성 확인용 `content_hash` 컬럼은 스키마에 있으나 사용하지 않는다. 우리 트랙(5.3)의 공식 예시 3종에 블록체인 항목이 없어, 억지로 넣기보다 상담 동선 완성을 택했다
- **DIP 빅데이터활용센터 민간데이터**(카드 매출·통신 생활인구) — 미신청·미확보. 관련 테이블은 스키마만 있고 0행이다
- **지역 한정 상품 매칭** — 달성군·북구 한정 상품 2건은 iM뱅크 취급이 확인됐는데도 지역 조건 매칭이 없어 노출되지 않는다
- **폐업률 감소 효과** — 측정하지 않았다
