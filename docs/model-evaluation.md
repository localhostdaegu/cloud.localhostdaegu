## 0. 왜 하는가 — 가용성

이 서비스는 **온라인과 오프라인 두 상황 모두에서 응대**해야 한다.

| 상황 | 경로 | 언제 |
|---|---|---|
| 온라인 | 외부 API — Gemini(gemini-embedding-001 · gemini-3.8-flash) | 평상시 운영. 키·네트워크가 정상일 때 |
| 오프라인 | 로컬 모델 — Ollama(qwen3-embedding:4b · bge-m3) | 외부 API 장애·키 한도 초과·비용 통제·네트워크 없는 시연/심사 환경 |

운영 경로는 외부 API(Gemini)를 쓴다. 하지만 **로컬 모델로 같은 일을 할 수 있는지 재 보지 않고 외부 API에만 기대는 건 곤란**하다. 그래서 외부 API 후보와 로컬 후보를 **같은 코퍼스(3,448건)·같은 질문(80건)·같은 지표**로 전부 평가했다. 이 문서가 그 증빙이다. 어느 한쪽만 평가한 것이 아니라, 로컬 3종(qwen 2560·1536, bge-m3 1024)과 외부 6종(Gemini 3072·2560·1536·1024, 그중 2560·1024는 API 직접 지정 실호출 포함)을 모두 돌렸다.

임베딩부터 시작한 이유: 검색 결과가 달라지면 그 위의 리포트 LLM이 아무리 좋아도 근거가 달라진다. 임베딩은 결정론적으로 비교할 수 있어 평가 비용도 가장 낮다.

로컬 후보를 bge-m3와 qwen3-embedding으로 잡은 이유는 **한국어 친화 임베딩 모델**이기 때문이다(사용자 결정). 둘 다 Ollama에 이미 내려받아 있다.

## 1. 자원·환경 (2026-09-18 실측)

| 항목 | 값 |
|---|---|
| GPU | NVIDIA GeForce RTX 5060 Ti 16 GB (driver 595.91.07) |
| Ollama | 0.31.2 · bge-m3 1.2 GB(F16, 상주 664 MB) · qwen3-embedding:4b 2.5 GB(Q4_K_M, 상주 4.4 GB) |
| Gemini | gemini-embedding-001, google-genai 1.29.0 |
| 코퍼스 | `rag_chunk` 3,448건 — funding 1,693(평균 412자) + news 1,755(평균 77자, 제목만) |
| 운영 DB 컬럼 | `vector(1536)` 고정 + HNSW 인덱스 |
| 코드 기준 | `dab254c` 위에서 작업 |

**제약**: DB 컬럼이 1536차원 고정이라 1024·2560차원 벡터는 저장할 수 없다. 그래서 이번 평가는 **DB 밖(numpy 코사인)** 에서 돌렸다. 운영 검색의 만료 공고 제외 필터는 적용하지 않았다(모델 비교가 목적).

## 2. 연구 질문

- **RQ1** 같은 코퍼스·같은 질문에서 로컬 임베더의 검색 정확도(Top-1·Recall@5·MRR)가 Gemini와 얼마나 차이 나는가.
- **RQ2** 로컬 임베더가 고르는 문서가 Gemini가 고르는 문서와 **얼마나 겹치는가**(교차 일치). 정확도가 같아도 다른 문서를 고르면 리포트 근거가 달라진다.
- **RQ3** 차원은 로컬 모델의 최고 차원(qwen 2560, bge-m3 1024)을 기준으로 삼고, Gemini를 같은 차원으로 맞췄을 때 손실이 있는가. 1536은 고집하지 않는다(사용자 결정).

| 후보 | 제공 | 차원 | 비고 |

| gemini-api@2560 | API(차원 직접 지정) | 2560 | 로컬과 같은 차원 실호출 — 절단 등가성 검증 겸용 |
| qwen@2560 | Ollama | 2560 | qwen3-embedding:4b 네이티브 최고 차원 |
| gemini@1536 | API | 1536 | **현 운영** |
| qwen@1536 | Ollama | 1536 | 현 Ollama 어댑터 기본값 |
| gemini@1024 | API(3072 절단) | 1024 | bge-m3 짝 |
| gemini-api@1024 | API(차원 직접 지정) | 1024 | 로컬과 같은 차원 실호출 |
| bge-m3@1024 | Ollama | 1024 | 고정 차원 |

**Gemini 차원 축소 실측**: `output_dimensionality`로 받은 1024·1536·2560 벡터는 3072 벡터의 앞부분을 잘라 정규화한 것과 코사인 **1.000000**(5문장 전부)으로 일치했다(MRL). 그래서 하네스는 3072만 호출하고 나머지는 잘라서 만든다(API 호출 4분의 1). 다만 **로컬과 같은 차원에서 실호출로도 재 봐야 한다**는 사용자 요구로 1024·2560은 `gemini-api@<dim>` 후보로 API에 차원을 직접 지정해 코퍼스 전량을 다시 임베딩했다 — 결과는 §6에서 절단 파생과 완전히 일치했다. API가 주는 지정 차원 벡터는 **정규화돼 있지 않다**(노름 0.62~0.88) — 운영 어댑터도 정규화를 하지 않지만 pgvector 코사인 거리는 노름에 무관해 검색엔 영향 없다.

**Ollama 차원 축소 실측**: qwen `dimensions=1536` 응답 대 2560을 잘라 정규화한 벡터의 코사인 평균 0.9997, 최소 0.9975. 사실상 같은 MRL 절단이다.

## 4. 절차

1. **어댑터 확장** (`backend/apps/rag/adapter/outbound/embeddings/`): Ollama 공통 베이스(`ollama_embedding_base.py`, Template Method) 위에 qwen(차원 인자)·bge-m3 어댑터를 두고, Gemini 어댑터에 `output_dimensionality` 인자를 추가했다. 기본 차원일 때 `model_name`은 기존 값 그대로라 DB `embedded_by`와 호환되고, 다른 차원이면 `-2560d` 같은 접미사가 붙어 혼용을 막는다. 레지스트리에 `bge-m3` 등록. 테스트 `tests/test_rag_embedding_adapters.py` 12건.
2. **평가셋 생성** (`generate_evalset.py`): 청크 텍스트를 gemma4:12b(Ollama, `think:false`)에 보내 "이 문서를 찾을 법한 질문 1개"를 만들었다. funding 60건(chunk_id 오름차순 앞 60 — 2025년 50·2026년 10) + news 20건, 전부 `status=candidate`(미검수). `--source-type news` 옵션과 `think` 차단을 이번에 추가했다.
3. **비교 하네스** (`compare_embedders.py`): 코퍼스 전량을 후보별로 임베딩(캐시 `data/eval/cache/*.npz`), 질문마다 source_type을 걸러 코사인 상위 10을 뽑는다. 테스트 `tests/test_rag_compare_embedders.py` 4건.

```bash
cd backend
python -m apps.rag.adapter.inbound.cli.generate_evalset --model gemma4:12b --limit 60 --source-type funding --output data/eval/rag_evalset_funding.jsonl
python -m apps.rag.adapter.inbound.cli.generate_evalset --model gemma4:12b --limit 20 --source-type news --output data/eval/rag_evalset_news.jsonl
cat ../data/eval/rag_evalset_funding.jsonl ../data/eval/rag_evalset_news.jsonl > ../data/eval/rag_evalset.jsonl
python -m apps.rag.adapter.inbound.cli.compare_embedders
```

## 5. 지표

- **Top-1**: 1위가 정답 청크. **Recall@5**·**MRR**: `evaluate_rag.py`와 같은 정의.
- **교차 일치**(로컬 ↔ 같은 차원 Gemini, 그리고 ↔ gemini@3072): Top-1 일치율, Jaccard@5, 전체 순위 Spearman ρ.
- **지연**: 질문 임베딩 p50 ms(80건), 문서 임베딩 처리량 docs/s(3,448건 1회).
- 평가셋이 전부 candidate라 `evaluate_rag.py`의 "본지표(confirmed)"는 없다. 아래 수치는 모두 **미검수 80건 기준**이다.

## 7. 해석

- **RQ1 — qwen@2560이 이 평가셋에선 Gemini보다 낫다.** Top-1 0.762 대 0.700, funding만 보면 0.883 대 0.783. 질문 단위로 qwen만 맞힌 게 8건, Gemini만 맞힌 게 3건이다. 다만 80건 표본에서 0.06은 질문 5개 차이라 "동급 이상"까지만 말할 수 있고 "우월"이라고 단정하지 않는다. 선행 프로젝트(22문장)에서도 qwen@2560과 Gemini는 0.909 대 0.955로 근접했다.
- **bge-m3는 뒤진다.** Top-1 0.650, Gemini만 맞힌 질문이 10건. 선행 프로젝트에서 bge-m3를 고른 이유는 정확도가 아니라 **VRAM 동주(로컬 LLM 두 개와 함께 상주)** 였다. 이 프로젝트는 로컬 LLM을 운영에 쓰지 않으므로 그 제약이 없고, 정확도 기준으론 qwen이 맞다.
- **RQ2 — 로컬과 Gemini는 다른 문서를 꽤 고른다.** Top-1 일치 0.71, Jaccard@5 0.45. 즉 정확도가 비슷해도 **근거 문서의 절반은 다르다.** 로컬로 전환하면 리포트 근거가 바뀌는 사례가 생긴다는 뜻이며, 이는 결함이 아니라 전환 시 알고 있어야 할 사실이다. 반면 Gemini 안에서 차원을 3072→1024로 줄여도 일치 0.89·ρ 0.99라 차원 축소 손실은 거의 없다.
- **같은 차원 실호출 검증**: API에 1024·2560을 직접 지정해 코퍼스 전량을 다시 임베딩한 `gemini-api@*`는 절단 파생 `gemini@*`와 80개 질문 전부에서 순위가 완전히 같았다(Top-1 일치·Jaccard@5·Spearman ρ 모두 1.000). 따라서 로컬 대 Gemini 같은 차원 비교(qwen@2560 대 gemini-api@2560 0.762 대 0.700, bge-m3 대 gemini-api@1024 0.650 대 0.738)는 절단 여부와 무관하게 성립한다.
- **RQ3 — 차원은 로컬 최고 차원에 맞춘다.** qwen은 2560이 1536보다 낫고(0.762 대 0.725), Gemini는 차원 손실이 미미하다. 따라서 로컬을 쓰면 2560, DB 컬럼도 그에 맞춰야 한다.
- **news 20건은 모든 모델이 Top-1 0.35~0.50.** 오답 12건을 열어 보니 제목이 완전히 같은 중복 기사는 1건뿐이고, 나머지는 **주제가 겹치는 다른 기사**였다(예: "수성구 관광 상권" 질문에 정답은 수성구청장 인터뷰, 1위는 수성못 관광 경쟁력 기사). 제목 한 줄에서 만든 질문이 너무 포괄적이라 생긴 평가셋 한계이지 모델 결함으로 보기 어렵다. news 수치는 순위 비교 용도로만 쓴다.
- **지연**: 로컬 질문 임베딩 p50 94~118 ms, Gemini 394 ms. 문서 색인은 bge-m3 94/s > Gemini 45/s > qwen 20/s. qwen으로 전량 재색인하면 3,448건에 약 3분.

**가용성 판정**
- **오프라인 응대 가능.** 검색은 로컬 qwen@2560이 외부 API와 동급 이상의 정확도를 내고, 리포트 생성은 로컬 gemma4:12b가 Gemini와 같은 게이트 전부 통과(1.000)를 낸다. 외부 API가 끊겨도 품질을 이유로 서비스를 멈출 필요는 없다.
- **오프라인 자원 한계 안에 든다.** 16 GB GPU를 비운 뒤 qwen3-embedding:4b(2560)와 LLM을 함께 올리면 gemma4:12b 11.6 GiB, kanana 9.0, exaone 8.9로 셋 다 동주한다(§10-4). 임베딩과 LLM을 번갈아 올렸다 내리는 지연 없이 응대할 수 있다.
- **온라인 응대 가능.** Gemini는 차원을 어떻게 잡아도(3072→1024) 결과가 거의 같아, 로컬과 같은 차원으로 맞춰 운영해도 손실이 없다.
- **두 경로의 결과는 같지 않다.** 정확도는 비슷해도 고르는 문서가 절반가량 다르다(Top-1 일치 0.71, Jaccard@5 0.45). 경로를 바꾸면 리포트 근거가 달라질 수 있음을 사용자에게 밝혀야 한다.
- **전환 장치는 준비돼 있다.** `EmbeddingPort` 뒤에 Gemini·qwen·bge-m3 어댑터가 있고 레지스트리(`_INDEX_EMBEDDER_REGISTRY`)의 provider 문자열로 고른다. 색인과 검색은 `embedded_by`로 같은 모델끼리만 비교하므로 두 경로가 섞이지 않는다.

### 10-2. 절차

- **입력은 운영 그대로.** 운영 수집 에이전트(`build_agents`)로 실제 DB에서 컨텍스트 3개를 채웠다 — review(대신동 카페, 재무 입력+질문 "원두값 오르면?"), review(삼덕동 일반음식점, 재무 없음), handoff(대신동 카페, 재무+상담 정보). 뉴스 5·공고 5·매칭 상품 9건이 프롬프트에 들어간다.
- **프롬프트는 운영 그대로.** LLM이 쓰는 섹션 6종(verdict·market·shock·funding·plan·questions)의 시스템 지시·프롬프트를 `report_text`에서 그대로 가져왔다. 여기에 verdict 방향 일치 짝(위험 등급만 red 82점 / green 18점으로 치환) 2개를 더해 **14 프롬프트 × 2회 = 후보당 28건**.
- **게이트는 결정론(LLM-as-judge 없음)** — 선행 프로젝트의 방식. 완료 / `#` 제목 금지 / 분량 상한(verdict 3문장·불릿 3개·질문 5개 등) / 대괄호 인용 금지 / **숫자 환각**(프롬프트에 없는 2자리 이상 숫자, 만 단위 환산 허용) / **인용 환각**(「」 안 제목이 문서 제목과 문장부호 무시 부분일치하지 않음) / 한국어 비율 ≥ 0.9 / **방향 일치**(red 짝 첫 문장에 주의·위험, green 짝에 양호·안정). 지연은 첫 조각(TTFT)·총 시간 p50, Ollama eval tok/s.
- **VRAM 동주**는 GPU를 비운 뒤 임베딩 → LLM → 임베딩 순으로 호출하고 `/api/ps`를 읽었다(§10-4).

### 10-5. 해석·결론

- **오프라인 리포트 작성기는 gemma4:12b.** 게이트 전부 통과 1.000으로 Gemini와 같고, 숫자 환각 0·인용 위반 0·방향 일치 1.000·반복 일치 14/14다. TTFT는 0.46 s로 Gemini(1.68 s)보다 빠르고 총 시간은 2.95 s로 0.8 s 느리다(48 tok/s). 출력이 Gemini의 56% 길이로 짧은 편인데 분량 상한 안에서 간결한 쪽이라 결함으로 보지 않는다.
- **kanana는 차선.** 빠르고(81 tok/s) 위반이 funding 인용 형식에 한정된다. 인용 표기 규칙을 프롬프트에서 더 강하게 못 박으면 올라올 여지가 있다.
- **exaone은 기준점으로만 읽는다.** 라이선스(NC) 때문에 애초에 운영 후보가 아니다. 한국어 특화 모델의 기준점으로 보면, 분량 지시(불릿 3개)를 절반 가까이 어기고 인용 표기를 키워드·질문에 남발하지만 숫자 환각 0·방향 일치 1.0·한국어 비율 1.0은 유지한다. 즉 이 프롬프트에서 한국어 모델의 바닥은 "사실은 지키되 형식 지시를 흘리는" 수준이고, gemma4와 kanana는 그 바닥보다 형식 준수에서 앞선다. 속도는 가장 빠르다(85 tok/s).

## 11. 운영 반영 — 차원 2560 통일과 오프라인 전환 절차 (2026-09-19)

**결정**: 운영은 Gemini를 쓴다. 오프라인(로컬) 경로는 시연 장애 대비 배선이고, 필요할 때 수 분 안에 바꿀 수 있어야 한다. 그러려면 온라인·오프라인 임베딩 차원이 같아야 하므로 **운영 Gemini 차원을 로컬 qwen과 같은 2560으로 맞췄다**(사용자 결정).

**적용 내용**
- 마이그레이션 `c1d2e3f4a5b6`: `rag_chunk.embedding` `vector(1536)` → **`halfvec(2560)`**. pgvector HNSW 인덱스는 `vector` 타입에서 2000차원까지만 지원한다는 것을 적용 중 실측했다(`column cannot have more than 2000 dimensions for hnsw index`). 2560은 fp16 `halfvec`(인덱스 4000차원까지)으로 저장하며 코사인 검색 정밀도 차이는 무시할 수준이다. 기존 1536 벡터는 형 변환이 불가해 비우고 전량 재색인한다.
- 어댑터 기본 차원: Gemini `EMBEDDING_DIM=2560`, qwen `DIMENSIONS=2560`(접미사 없는 `model_name`이 이제 2560을 뜻한다). 설정 `RAG_EMBEDDING_PROVIDER`(기본 gemini)·`REPORT_WRITER_PROVIDER`(기본 gemini)·`OLLAMA_REPORT_MODEL`(기본 gemma4:12b).
- 재색인: `build_rag_index --full --provider gemini` — 3,589청크, 2분 33초, 429 없음. `alembic check` 통과, 백엔드 테스트 497건 통과.
- 검증: 재색인 후 평가셋 80건을 운영 검색 경로(`evaluate_rag`)로 돌리면 Recall@5 0.438이 나오는데, funding 20건을 **만료 공고 필터를 끄고** 돌리면 Recall@5 1.000·MRR 0.91이다. 평가셋의 funding 정답이 2025년 공고(만료)라 운영 필터에 걸리는 것이지 색인 문제가 아니다. 평가셋을 검수할 때 만료되지 않은 공고로 다시 뽑아야 한다.

**오프라인 전환 절차(시연 장애 시)**

```bash
# 1) 로컬 모델 준비 확인 (둘 다 상주 시 약 11.6 GiB)
ollama pull qwen3-embedding:4b && ollama pull gemma4:12b
# 2) 검색 색인을 로컬 임베더로 교체 (3,589청크 약 3분, 20 docs/s)
cd backend && python -m apps.rag.adapter.inbound.cli.build_rag_index --full --provider ollama
# 3) 환경변수 2개 바꾸고 백엔드 재시작
RAG_EMBEDDING_PROVIDER=ollama REPORT_WRITER_PROVIDER=ollama uvicorn main:app --port 8300
```

되돌리기는 `--provider gemini`로 재색인(약 2.5분)하고 환경변수를 원래대로 두면 된다. 색인은 `embedded_by`로 모델을 기록하므로 질의 임베더와 색인 모델이 어긋나면 검색 결과가 0건이 된다 — 재색인 없이 환경변수만 바꾸면 안 된다.
